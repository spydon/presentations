# Passkeys with supabase_flutter

A [flutter_deck](https://pub.dev/packages/flutter_deck) presentation about
passkeys in [supabase_flutter](https://pub.dev/packages/supabase_flutter) v3.
The last slide is a live Q&A: the audience scans a QR code, creates a passkey
on their phone and posts questions that pop up on the slide in real time.

One Flutter web build serves both parts:

- `/` is the deck.
- `/?qa` is the audience page that the QR code points to.

## Project layout

| Path                         | What it is                                                       |
| ---------------------------- | ---------------------------------------------------------------- |
| `lib/deck/`                  | The slides, the QR code and the live question wall               |
| `lib/qa/`                    | The audience page: passkey sign up and sign in, asking questions |
| `lib/supabase_schema.g.dart` | The typed schema, generated by `supabase_typegen`                |
| `supabase/migrations/`       | The `questions` table, RLS policies and realtime publication     |
| `web/passkeys_bundle.js`     | The browser side of `passkeys_web`, see below                    |

## Deployment

Everything deploys on push to `main`:

- **The web build** goes to
  <https://presentations.spydon.dev/supabase_flutter_passkeys/> with the other
  presentations. The audience page is
  <https://presentations.spydon.dev/supabase_flutter_passkeys/?qa>.
- **The database and auth settings** go to the Supabase project through the
  Supabase GitHub integration, with `supabase_flutter_passkeys` as its
  Supabase directory and "Deploy to production" turned on. It applies the
  migrations in `supabase/migrations/` and the settings in
  `supabase/config.toml`. They hold the production values, since the
  dashboard compares the project against them. Email confirmation is turned
  off, since guest accounts get a generated address on `GUEST_EMAIL_DOMAIN`
  that never receives mail. Only the relying party differs per environment:
  `[remotes.production.auth.webauthn]` sets it to `presentations.spydon.dev`.

Passkeys only work over HTTPS on the relying party domain, so phones have to
use the deployed site.

## Running locally

```sh
flutter run -d chrome --web-port 8080
```

Against the hosted project, passkeys fail on localhost because the relying
party is `presentations.spydon.dev`. The local stack (`supabase start`) uses
`localhost` as its relying party instead, see `[auth.webauthn]` in
`supabase/config.toml`:

```sh
flutter run -d chrome --web-port 8080 \
  --dart-define=SUPABASE_URL=http://127.0.0.1:54321 \
  --dart-define=SUPABASE_PUBLISHABLE_KEY=<key from supabase status>
```

The QR code points at the page the deck is served from. To present from a
local build, point it at the deployment instead with
`--dart-define=QA_URL=https://presentations.spydon.dev/supabase_flutter_passkeys/?qa`.
Other build time settings are in `lib/config.dart`.

## Testing

```sh
flutter analyze
flutter test
```

The tests render every slide except the live Q&A at 1920x1080 and fail on
overflow.

## Regenerating the typed schema

Regenerate `lib/supabase_schema.g.dart` after every schema change, with
Supabase CLI 3.0 or newer:

```sh
supabase gen types --lang dart --remote > lib/supabase_schema.g.dart
```

## About `web/passkeys_bundle.js`

`passkeys_web` expects a `PasskeyAuthenticator` JavaScript global, which
upstream ships as a `bundle.js` release asset. There is no published asset for
`passkeys_web` 2.11.0, so this is a dependency free port of its
`javascript/src` that defines the same global.
